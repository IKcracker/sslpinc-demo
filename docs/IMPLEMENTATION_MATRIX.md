# SSLP RFP coverage / custom-code alternative

The posted RFP asks for WordPress/Gutenberg. This independent concept is deliberately **React/Vite custom code** and would only proceed as a WordPress alternative if the client explicitly approves the platform change.

| Requirement | Proposal demo | Contracted production acceptance |
| --- | --- | --- |
| Public page architecture | Home, About, Team, Services, Evaluations, Resources, Referrals, Careers, Contact | Final approved pages and client-supplied clinical content |
| Three new services | Community Integration, JASPER, Myofunctional pages with reusable template | Clinical approval, metadata and final service descriptions |
| Maintainability | Functional local browser studio for text, team, services, FAQs and resources | Authenticated durable CMS, drafts, media, roles, revisions, owner training and video |
| Legacy SEO | Static route prerender, unique metadata, canonical, sitemap, schema, migration documents | Authorized crawl, complete verified mapping, 301 tests, GSC/GA4 configuration |
| WCAG 2.2 AA | Semantic HTML, keyboard-operable controls, visible focus, error feedback, reduced motion | Automated + manual NVDA/VoiceOver/keyboard tests, remediation, signed report |
| Performance | Lightweight, custom CSS, vector illustrations, no page builder | LCP/CLS/INP and mobile performance budgets agreed from baseline, verified on deployed production |
| Security | Public sample copy; no real contact, PHI or staff data | Security architecture, auth, audit, backup/restore test, secure forms and privacy review |
| Staging | Separate preview domain; noindex | Protected client staging, incumbent live site unaffected, written approval before cutover |
| Content migration | No real data copied into proposal demo | Authorized and approved source content transfer with references and QA |
| Contact | Client-side test validation; nothing sent | Approved secure delivery/retention and anti-spam controls |
| Support | Not contracted | Minimum 30-day post-launch defect support and migration monitoring |

## Suggested staged delivery after agreement

1. Weeks 1–2: Discovery, permissions, old-site inventory, SEO benchmark and content plan.
2. Weeks 3–4: Visual design confirmation and custom authenticated editing architecture.
3. Weeks 5–7: Reusable page components, CMS content models, secure forms and migration content.
4. Weeks 8–9: SEO migration/redirect implementation, accessibility pass and automated regression tests.
5. Weeks 10–11: Client acceptance, training, documentation, final content, staging and launch gate.
6. Week 12: Cutover and active monitoring (30-day support clock begins at launch).

Timeline indicative; discovery, RFP approval and information access may change estimates. See `docs/SEO_MIGRATION_PLAN.md` and `docs/ACCESSIBILITY_QA.md`.
